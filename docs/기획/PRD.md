# 틈튼(TMTN) 제품 요구사항 문서

버전 2.1 · 2026-09-16 · 현재 로컬 개발본 기준 ([변경·검증 범위](../ui-review-2026-09-16/README.md))

문서 소유 역할: 제품 기획. 화면은 디자인·Android, API와 저장은 백엔드, 추론과 공개 범위는 모델 담당자가 함께 검토한다. 구체적인 담당자와 일정은 팀에서 배정한다.

이 문서는 [PR #17](https://github.com/AI-HealthCare-05/AH_05_01/pull/17)의 Android와 [PR #15](https://github.com/AI-HealthCare-05/AH_05_01/pull/15)의 서버를 설명한다. 기준 커밋·문서 우선순위는 [문서 안내](README.md)에 있다. **현재 구현, 기존 시험 결과, 앞으로 필요한 작업을 구분하며 운영 출시 완료를 선언하지 않는다.**

## 1. 제품의 목적과 대상

틈튼은 일상에 들어갈 작은 행동을 카드 한 장으로 선택하고, 실천 기록과 모은 재료를 통해 습관을 이어 가는 앱이다. 틈튼이 캐릭터와 댐의 변화는 실천이 쌓인 모습을 보여 준다. 틈튼일보는 그 기록을 읽기 쉬운 일간·주간 이야기로 묶는다.

주요 대상은 큰 운동 계획보다 짧은 움직임, 근력운동, 생활리듬, 식사·기록, 수분 관련 행동부터 시작하려는 성인 사용자다. 매일 같은 강도를 강요하지 않고 직접 선택·쉬어가기·추가 운동의 선택지를 둔다.

틈튼지수와 허리둘레 추정은 참고 정보다. 질병의 진단, 발병 확률, 실제 측정값으로 설명하지 않는다. 점수·등수의 높고 낮음을 카드 보상 또는 사용자 자격으로 사용하지 않는다. 지원 연령·입력 범위·임신 상태에 따른 분석 가능 여부는 서버·모델 응답을 따른다.

Google 경로가 있다는 것과 운영 OAuth가 설정됐다는 것은 다르다. 현재 전달용 테스트 APK에는 웹 클라이언트 ID가 없어 팀 설정·서명으로 빌드한 뒤 실제 인증을 확인해야 한다.

**후속 검토 자료:** SHAP/XAI 개인 해설, 출처 기반 읽을거리 선택 파이프라인은 별도 검토·개발 자료다. 현재 Android의 신문 문장은 코드의 상태별 고정 문장과 기록 조합이며, 운영 LLM·SHAP 기사 생성 기능으로 설명하지 않는다.

## 4. 사용자 여정

1. 앱을 처음 연 사용자는 브랜드 소개 후 Google·이메일·기존 계정 로그인을 선택한다.
2. 신규 사용자는 인증과 동의를 진행하고 기본·신체·운동 정보를 입력한다. 생활시간 설정은 건너뛸 수 있다. 입력 확인 → ‘첫 댐 만나기’ → 실제 댐 상태 안내 → ‘오늘 카드 만나기’로 이어진다. 입력 확인과 첫 댐 안내는 체크포인트로 재개한다. 첫 공개로 재개하면 이미 확인한 요약의 기본값을 다시 보여 주지 않는다.
3. 카드 3장 중 1장을 골라 확정한다. 확정 전에 다시 고를 수 있고, 확정 후에는 오늘의 선택을 유지한다.
4. 직접 확인·타이머·센서 방식에 따라 행동을 수행한다. 목표 충족과 최종 완료 처리를 구분한다.
5. 완료하면 재료가 쌓이고 기록·일보에 반영된다. 더 움직이고 싶으면 틈새 운동을 선택한다.
6. 일보·기록·댐을 확인하고, 내 정보에서 입력이나 설정을 관리한다.

자세한 분기와 오류 복구는 [유저 플로우](유저플로우.md)를 따른다.

첫 댐은 기존 서버 상태를 읽는다. 현재 Figma A21/A32와 서버는 재료 0~4개를 0단계, 5개부터 1단계로 정한다. 가입·소개 화면 열기만으로 보상을 주지 않는다. 실제 1단계로 시작하는 변경은 별도 제품 결정이며, 이번 복원은 [첫 댐 안내와 검증](../ui-review-2026-09-16/FIRST-DAM.md) 범위다.

## 5. 입력과 저장 규칙

### 5.1 기본·신체 정보

- 이름·별명·생년월, 성별·해당 시 임신 상태, 키(cm)·몸무게(kg)를 현재 가입 흐름에서 받는다. 생년월은 연·월이며 정확한 생일을 받은 것으로 취급하지 않는다.
- 내 정보의 화면명은 **신체 정보**다. 성별은 해당 수정 화면에서 읽기 전용이다. 키·몸무게 저장 요청에는 성별을 넣지 않는다.
- 이 제한은 현재 UI 정책이다. 서버의 범용 프로필 API가 성별 수정을 전역 차단하도록 변경된 것은 아니다.
- 입력 스냅샷과 예측 결과는 구분한다. 입력 저장 성공만으로 최신 예측 결과 생성·공개 성공을 표시하지 않는다.

### 5.2 근력운동: 첫 입력 A16-안

현재 화면은 ‘평소 일주일’에 운동하는 **요일**을 고르게 한다. 한 날에 아침·저녁으로 운동해도 1일이다. 달력 날짜별 수행 기록이나 지난주의 실제 운동 로그를 수집하는 기능은 아니다.

| 선택 | 화면에서 확인하는 값 | 기존 서버 요청 |
| --- | --- | --- |
| 선택 없음 | 주 0일 / 안 함 | `strength_weekly_count=0`, `strength_intensity=null` |
| 1~4개 요일 | 주 1~4일 | 해당 일수 1~4 |
| 5개 요일 | 주 5일 | 5 |
| 6~7개 요일 | 현재 선택한 6~7일 | 5, 기존 ‘5일 이상’ 구간 |

요일 집합은 현재 화면 상태에만 있다. 서버에는 개별 요일과 정확한 6·7일을 저장하지 않는다. 기존 값으로 복귀했을 때는 저장된 일수만 안내하고 월·수·금 등을 임의로 선택하지 않는다. 운동일이 있으면 강도 `LIGHT / MODERATE / HARD` 중 하나를 고른다.

Figma의 A16 요일 UI는 `A08ExerciseScreen` 안의 근력 부분에 적용됐다. 내 정보의 기존 운동 수정 화면은 일수 선택을 유지한다. 두 화면이 저장하는 계약은 같다.

### 5.3 유산소·생활시간

- 저·중·고강도의 주당 분 입력과 저장 흐름은 기존대로 유지했다.
- 운동 습관 요청은 다음 **5개 필드**다. 요일·날짜·추가 메타데이터를 붙이지 않는다.

```json
{
  "strength_weekly_count": 3,
  "strength_intensity": "MODERATE",
  "aerobic_low_minutes": 60,
  "aerobic_moderate_minutes": 90,
  "aerobic_high_minutes": 0
}
```

위 값은 계약 설명용 예시이며 실제 사용자 데이터가 아니다. 현재 서버 DTO의 유산소 값은 기본 0인 정수다. ‘아직 입력하지 않음’과 ‘실제 0분’을 별개 값으로 보존한다는 옛 요구사항은 구현 완료로 볼 수 없다.

생활시간은 기상·점심·취침 설정 및 알림에 사용한다. 현재 peer 점수 전달 코드의 `bedtime`, `wakeTime`은 여전히 `null`이다. 설정 화면이 있다는 이유로 이 값이 이미 점수 계산에 반영된다고 설명하지 않는다.

## 6. 카드·미션·센서 규칙

### 6.1 오늘의 카드

- 서버가 서비스 날짜 기준 카드 세트를 생성·조회한다. 선택 후보 수는 3개다. 카드 카탈로그의 전체 개수는 현재 서비스 데이터로 결정하며 과거 ‘200개’를 고정 요구사항으로 쓰지 않는다.
- 한 장 확정은 서버에서 제한한다. 이미 선택한 요청·중복 확정의 충돌은 현재 상태를 다시 확인하는 경로로 처리한다.
- 카드 내용·미션 유형·목표·재료는 서버 스냅샷을 따른다. UI가 임의로 난도·보상량을 바꾸지 않는다.
- ‘쉬어가기’, ‘포기’, ‘일시정지’, ‘완료’를 서로 다른 상태로 다룬다. 앱을 나갔다고 자동으로 쉼이나 완료가 되지 않는다.

### 6.2 실행 방식

| 방식 | 현재 동작 | 완료 기준 |
| --- | --- | --- |
| 직접 확인 | 사용자가 수행 여부 확인 | 사용자의 완료 요청 및 서버 결과 |
| 타이머 | 시작·일시정지·재개·중단과 누적 시간 표시 | 목표 충족 후 완료 요청. 시간 도달만으로 보상을 확정하지 않음 |
| 센서 | 걸음·활동 시간·계단·달리기 거리 등 유형별 측정 | 해당 센서 누적값·서버 동기화·완료 처리 결과 |
| 대체 흐름 | 필요한 센서나 권한을 사용할 수 없을 때 안내 후 직접 확인 경로 | 동일 미션·재료를 유지하며 대체 방식을 표시 |

센서 미션의 카드 외형은 다른 미션과 같은 중립 테두리를 사용한다. 측정 방식은 작은 설명으로 구분한다. 제목·목표·보상·측정 설명을 한 줄에 모두 합쳐 과밀하게 만들지 않는다.

거리는 **현재값·목표 모두 m**로 표시한다. 내부 측정값을 km로 바꿔 저장하는 변경은 없다. 표시 시 소수 부분은 올려서 목표 달성처럼 보이지 않게 버린다. 예: `0 m / 목표 200 m`.

센서 기록의 로컬 보관·동기화 경로는 존재한다. 이것을 모든 가입·카드 선택·보상이 인터넷 없이 완료된다는 보장으로 확대하지 않는다. 동기화 대기와 서버 완료를 구분하며 앱 종료·재접속·중복 전송은 별도 회귀 검증 대상이다.

### 6.3 틈새 운동

- 오늘의 카드를 완료해야 시작할 수 있다. 남은 횟수·목록은 서버 응답을 사용한다.
- 보상 한도는 서비스 날짜당 2회이며, 운동 한 번을 완료하면 해당 재료 1개를 받는다.
- 서버는 오늘 카드 미완료, 보상 한도 소진, 진행 중 세션, 선택 불가능한 운동 등의 요청을 거절한다. 그 사유를 사용자에게 보여 준다.
- 추가 운동은 별도 세션·보상 슬롯으로 기록한다. 같은 날 추가 운동을 했다고 ‘실천한 날’을 2일·3일로 늘리지 않는다.
- 신문은 기존 추가 운동 기록 API를 읽는다. 404·501로 해당 조회가 지원되지 않으면 그 부가 영역만 생략하고, 다른 실패는 조회 실패 상태로 구분한다.

## 7. 기록·날짜·쉬어가기

| 개념 | 기준 |
| --- | --- |
| 홈·기록의 최근 7일 | 서비스의 오늘을 포함한 최근 7일 |
| 틈튼일보 주간면 | 서비스의 오늘이 속한 월요일~일요일. 날짜·실천 일수·해낸 카드·재료를 같은 범위로 집계. 미래 날짜는 비활성화 |

서비스 날짜는 서버의 날짜 응답을 존중한다. 현재 서버는 계정별 테스트 날짜 오프셋도 포함한다. 디버그 날짜 도구는 테스트용이며 운영 UI나 실제 기록으로 소개하지 않는다. 자정·월 변경·가입일 경계는 실제 서버 연결 검증이 필요하다.

## 8. 틈튼일보와 건강 참고 정보

### 8.1 신문의 내용과 행동 연결

일보는 현재 기록으로 구성하는 **주간면·일간면**이다. 주간면은 월요일~일요일로 고정하고 서비스 날짜를 기준으로 계산한다. 홈과 기록의 최근 7일은 그대로 유지한다. 기록 없는 상태에도 0개 실천을 실패로 몰아붙이지 않고 첫 카드 선택으로 안내한다. 주간/일간 자료의 날짜 범위를 표시한다.

상단 ‘새로고침’ 버튼과 ‘불러오는 중’ 텍스트는 제거됐다. 자동 조회·재조회와 영역별 실패 상태까지 없앤 것은 아니다. 읽기를 마친 사용자는 현재 카드 상태에 맞는 진입 버튼으로 이동한다. 예전 ‘신문을 덮으며’와 같은 불명확한 문구를 복원하지 않는다.

캐릭터는 현재 수채화 스타일 에셋을 사용하고 댐·캐릭터 이미지의 비율을 유지한다. 제목, 짧은 설명, 본문, 보조 정보를 구분한다. 실천 기록·댐 재료와 건강 참고 지표는 서로 다른 정보로 표시한다.

### 8.2 틈튼지수

- 앱의 peer 연결은 `GET /tuntun-score/peer/v2`를 사용한다. 예전 mock API와 다른 계약이다.
- 종합 점수와 영역별 또래 위치를 구분한다. **종합 점수를 등수로 표시하지 않는다.** 영역은 `physical`, `diabetes`, `hypertension`, `lifestyle` 키로 연결한다.
- 신문의 종합 표시에는 `scoreAvailable`, `isMock`, 사용 가능 영역 2개 이상, 유효한 수치가 필요하다. 영역별 미산출은 해당 이유를 유지한다.
- 옛 ‘관심 0~39 / 보통 40~69 / 양호 70~100’ 구간을 peer 결과에 덧붙이지 않는다. 모델 결과를 임의로 고정 80점 등으로 대체하지 않는다.
- 현재 서버는 분석 동의 `HEALTH_REFERENCE_ANALYSIS`가 없으면 403, peer 브릿지가 미설정·접속 불가이면 503을 반환한다.
- 현재 입력은 최신 기본·신체·평소 운동 습관이다. ‘최근 7일 중 5일 완료해야 산출’ 또는 ‘미션 완료 직후 그 운동량이 자동으로 점수에 합산’되는 규칙은 현재 구현이 아니다.
- 코드와 모델 패키지에 검토용·운영 공개 보류 표기가 남아 있다. UI 표시 연결만으로 모델의 운영 승인과 배포가 끝난 것으로 판단하지 않는다.

### 8.3 허리둘레 추정

흐름은 **신체정보 또는 운동 습관 저장 → 서버의 재계산 시도 → 예측 결과 저장 → 공개 가능한 결과 조회 → 앱 표시**다. 최신 서버에는 재계산 연결이 이미 있다.

| 상태 | 현재 처리 |
| --- | --- |
| 브릿지 URL 미설정 | 계산 생략. 입력 저장은 성공할 수 있음 |
| 필요한 신체·운동·생년월 정보 부족 | `INPUT_MISSING` 저장 경로 |
| 모델 통신·범위 오류 | `FAILED`·`OUT_OF_RANGE` 등 결과 경로. 입력 저장 자체는 유지 |
| 계산 성공 | `WAIST_CM_ESTIMATE`, `COMPUTED`, 소수 첫째 자리 결과 저장 |

현재 허리둘레 서비스에는 해당 서브모델의 성공 결과를 `SYSTEM_AUTO_APPROVAL`로 자동 승인하는 코드도 있다. ‘항상 사람이 승인한다’는 설명은 맞지 않는다. 수동 승인 해제 후 재계산 시 다시 활성화될 수 있는 부분은 담당자 검토 사항이다.

최신 공개 조회는 최신 **성공** 결과를 찾는다. 이후 계산이 실패하면 과거 성공 결과가 남을 수 있으며, 앱은 현재 입력 버전과 일치 여부를 추가 검사하지 않는다. 계산 일시를 확인하고 ‘이번 저장값으로 방금 계산 완료’라고 단정하지 않는다. 이 한계와 분석 동의 적용 범위는 [개정대조](개정대조.md)에 후속 과제로 남겼다.

## 11. UI·모션 기준

현재 앱의 차콜·크림 톤, 주황 포인트와 수채화 캐릭터를 유지한다. 아래는 **코드에서 확인한 값**이며 이번 문서에서 새로 정한 디자인 값이 아니다. 모든 화면이 하나의 숫자만 쓰도록 강제하지 않는다.

| 요소 | Android의 현재 공통 기준 |

모션은 **ms와 전환 조건**으로 정의한다. 60Hz에서 240ms가 약 14~15프레임에 해당하는 것은 환산 예시일 뿐, 실제 앱이 고정 프레임 수나 60fps를 보장한다는 뜻이 아니다. 터치 처리 자체를 애니메이션 끝까지 지연시키지 않는다.

일반 폭에서는 미션 제목을 간결한 한 줄로 유지하되, 큰 글자·좁은 폭에서는 전체 정보 접근을 우선한다. 근력 요일 버튼은 폭과 글자 배율에 따라 여러 줄로 재배치한다. 내용 잘림이나 작은 터치 영역으로 한 줄을 강제하지 않는다.

Android 텍스트는 sp, 나머지 UI는 dp다. **iOS 앱 구현은 이번 기준 코드에 없다.** iOS는 별도 개발 시 pt·Dynamic Type에 맞춰 정하며 Android 값을 그대로 확정값으로 복사하지 않는다. 라이트 화면이 이번 시각 검증 범위이며 다크 모드 전체 화면 검수 완료로 표시하지 않는다.

2. 팀 서버·OAuth·서명으로 빌드해 신규·기존 로그인, 온보딩 재개, 카드 확정·완료·쉼, 추가 운동 한도와 보상 중복을 확인한다.
3. 권한 거부·센서 미지원·백그라운드·앱 종료·네트워크 복구·실외 거리 측정과 알림을 확인한다.
4. peer·허리둘레의 동의·지원 입력·미설정·실패·오래된 결과·모델 공개 정책을 확인한다.
5. 탈퇴·기록 삭제·CSV 범위·오류 처리를 실제 저장 데이터와 대조한다.

현재 운영 지표를 측정했다고 주장하지 않는다. 다음은 **제안 지표이며 목표 수치는 미정**이다: 가입 시작→완료율, 첫 카드 확정→완료율, 최근 7일 실천 일수, 틈새 운동 진입→완료율, 화면 조회 실패율, 센서 동기화 실패율, 의도치 않은 중복 보상 수. 이벤트 수집 동의·필드·집계 정의를 팀이 먼저 정한다. 건강 입력 원문을 분석 이벤트에 넣지 않는다.
